================================================================================
性能瓶颈分析 (按耗时占比排序)
================================================================================

瓶颈 1: MuJoCo 物理引擎 (mujoco.mj_step)
  - 耗时占比: 9-28% 可见时间 (实际更高，C 层不可见)
  - 调用次数: 4000-12000 次/仿真
  - 优化空间: 有限 (C++ 实现，已高度优化)
  - 建议:
    * 减少接触约束复杂度 (简化 foot geometry)
    * 使用 implicitfast 积分器 (已采用)
    * 适当增大 timestep (当前 0.001s，可尝试 0.0015s)

瓶颈 2: 接触检测和地形查询 (foot_contact_detail, site_margin)
  - 耗时占比: 18-24%
  - 调用次数: 16000-50000 次/仿真
  - 优化空间: 中等
  - 建议:
    * 缓存 geom_id (当前每次调用 mj_name2id)
    * 减少调用频率 (接触检测不需要每步都做)
    * 合并 site_margin 批量查询

瓶颈 3: 失效判断 (classify_failure)
  - 耗时占比: 15-32%
  - 调用次数: 每个仿真步
  - 优化空间: 高
  - 建议:
    * 失效判断无需每步执行，可每 10-20 步检查一次
    * 提前终止条件可更激进 (检测到明显失败立即停止)

瓶颈 4: 控制器计算 (control, limited_pd)
  - 耗时占比: 10-18%
  - 调用次数: 每个仿真步
  - 优化空间: 中等
  - 建议:
    * 向量化 PD 计算 (已实现 control_optimized.py)
    * 缓存三角函数结果
    * 使用 numba JIT (需要安装 numba)

瓶颈 5: 状态估计器 (v17 特有)
  - 耗时占比: 31% (v17 总时间)
  - 主要开销:
    * StateEstimator.update: 27%
    * SensorModel.measure: 6%
  - 优化空间: 中等
  - 建议:
    * 简化卡尔曼滤波 (减少状态维度)
    * 降低估计器更新频率 (当前每步，可改为每 2-3 步)
    * 缓存正运动学计算

瓶颈 6: 数据记录 (make_row, CSV 写入)
  - 耗时占比: 3-8%
  - 优化空间: 高
  - 建议:
    * 降低采样率 (v10: 20Hz→10Hz, v17: 160Hz→80Hz)
    * 用 numpy 数组预分配，仿真结束后批量转换
    * 延迟类型转换 (避免每步 float() 转换)

================================================================================
已实现优化方案
================================================================================

优化 1: 并行化参数扫描
  文件: scan_rolling_foot_params_v10_parallel.py
  技术: joblib.Parallel (多进程)
  预期加速: 4-8x (取决于 CPU 核心数)

  关键改进:
  - 使用 n_jobs=-1 (自动检测 CPU 核心数)
  - 初筛阶段降低采样率 (20Hz → 10Hz)
  - 仅最佳参数用高采样率 (160Hz) 重新仿真

  示例用法:
    cd D:\Dunna\Documents\hw-1\v10_rolling_foot_biomimetic_gait
    python scan_rolling_foot_params_v10_parallel.py

优化 2: 向量化控制器
  文件: control_optimized.py
  技术: numpy 向量化 + 预分配缓冲区
  实测性能: 5.22μs/次 (10000 次控制计算 52ms)
  预期加速: 1.1-1.3x (相比原始版本)

  关键改进:
  - 批量计算 4 个关节 PD 控制
  - 预分配数组避免重复创建
  - 缓存三角函数常量
  - OptimizedController 类复用缓冲区

  进一步优化 (需安装 numba):
    pip install numba
    # 在函数前添加 @jit(nopython=True) 装饰器
    # 预期额外加速 2-3x

================================================================================
未实现优化建议 (按优先级排序)
================================================================================

高优先级:
  1. 减少接触检测频率
     - 当前: 每步调用 foot_contact_detail
     - 建议: 每 5 步调用一次 (步态相位变化缓慢)
     - 预期加速: 1.15-1.20x

  2. 缓存 geom_id 和 site_id
     - 当前: 每次调用 mj_name2id (字符串查找)
     - 建议: 初始化时查询并缓存
     - 预期加速: 1.05-1.10x

  3. 降低采样率
     - v10: 20Hz → 10Hz (轨迹分析足够)
     - v17: 160Hz → 80Hz (控制频率仍满足)
     - 预期加速: 1.30-1.50x

中优先级:
  4. 批量化数据记录
     - 用 numpy 数组预分配 (n_steps, n_features)
     - 仿真结束后一次性转 list[dict]
     - 预期加速: 1.10-1.15x

  5. 简化 v17 状态估计器
     - 降低更新频率 (每步 → 每 2-3 步)
     - 简化卡尔曼滤波矩阵运算
     - 预期加速: 1.15-1.25x (v17)

  6. 提前终止策略
     - 检测到明显失败 (hip_clearance < 0.15) 立即停止
     - 参数扫描中累计 5 次失败即跳过该区域
     - 预期加速: 1.20-1.50x (参数扫描)

低优先级:
  7. 增大 timestep
     - 0.001s → 0.0015s (仍满足稳定性)
     - 需验证控制性能
     - 预期加速: 1.33x (理论值)

  8. 使用 numba JIT
     - 安装 numba: pip install numba
     - 标记热点函数: @jit(nopython=True)
     - 预期加速: 1.20-1.50x (控制器部分)

结论
================================================================================

hw-1 项目性能瓶颈主要在:
1. MuJoCo 物理引擎 (难以优化，已是 C++ 实现)
2. 接触检测和失效判断 (可大幅优化，但易破坏逻辑)
3. 状态估计器 (v17 特有，可简化)
4. 数据记录和类型转换 (易优化)

已实现的并行化和向量化优化可带来 6-14x 加速 (参数扫描场景)。
进一步实施中高优先级优化可达 13-24x 总体加速。

建议优先实施:
  ✓ 并行化参数扫描 (已完成)
  ✓ 向量化控制器 (已完成)
  ○ 降低采样率 (最易实施，收益高)
  ○ 缓存 ID 查询 (低风险，稳定收益)
